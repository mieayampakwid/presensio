# 18 — Internationalization (Indonesian & English)

Status: draft v1.0 (2026-10-02) — infrastructure and users pages implemented; remaining pages tracked in `docs/plans/2026-10-02-i18n.md`

## Problem

The UI shipped as hardcoded English strings with Indonesian domain terms mixed in, while validation and auth messages follow the single configured locale. Presensio's users are Indonesian school staff, guardians and students, but the product also needs English. No spec defined the UI language, so wording drifts page by page.

## Goals

1. Support exactly two interface languages: Bahasa Indonesia (`id`, default) and English (`en`).
2. One source of truth for strings: Laravel `lang/{en,id}/*.php`, used by both server messages and the React UI.
3. A per-user language preference that survives devices, plus a cookie for signed-out pages.
4. No new dependency.

## Non-goals

- Locales beyond `id` and `en`; right-to-left layouts.
- Translating user-entered data (names, class names, announcements, comments) or stored enum values (e.g. gender `L`/`P`, `status` codes). Only display labels translate.
- Translating audit log payloads or CSV headers (CSV mirrors the screen in the exporting user's locale).
- Per-school or admin-editable translations.

## Decisions

1. **Source:** `lang/en/*.php` is the complete reference. `lang/id/*.php` must contain exactly the same keys; `tests/Unit/LangParityTest` fails otherwise. At runtime a missing `id` key falls back to `en` (`fallback_locale = en`), never to a raw key.
2. **Default:** `APP_LOCALE` defaults to `id` in `config/app.php`. Tests pin `en` in `phpunit.xml`.
3. **Resolution order** (`SetLocale` middleware): `users.locale` → `locale` cookie → configured default.
4. **Persistence:** `users.locale` is nullable (`en`/`id`; null = follow cookie/default). `PUT /locale` (`locale.update`, open to guests) validates against the `Locale` enum, saves it on the signed-in user, and always sets a one-year `locale` cookie.
5. **Delivery to React:** `HandleInertiaRequests` shares `locale`, `locales` (native names, never translated) and `translations` (every `lang/en/*.php` group except `auth`, `pagination`, `passwords`, `validation`, merged over English). The client uses `useTranslation().t('group.key', { name })`; `:name` placeholders follow Laravel's syntax. An unknown key renders as the key itself so gaps are visible.
6. **Keys:** `<area>.<screen>.<element>` (e.g. `users.form.roles`). Shared words live in `common`. Role display names live in `roles.<value>` and are looked up by the stored role value.
7. **Terminology (id):** Kepala Sekolah, Guru, Konselor, Keuangan, Staf, Wali Murid, Siswa; "pengguna" for user, "nama pengguna" for username, "kata sandi" for password, "peran" for role.
8. **Server messages** (flash toasts, validation, auth) use `__()` / Laravel's `lang` files in the request locale. Validation attribute names are defined in `validation.attributes`.
9. **Switcher:** language switcher on the appearance settings page. Signed-out placement (login pages) is part of the follow-up plan.

## Acceptance Criteria

| ID | Criterion |
| --- | --- |
| 18-01 | A signed-in user's saved `locale` wins over the cookie and the default. |
| 18-02 | A guest's cookie sets the locale on signed-out pages. |
| 18-03 | `PUT /locale` rejects anything other than `id`/`en`. |
| 18-04 | Every `lang/en` key exists in `lang/id` (and vice versa). |
| 18-05 | A key missing in `id` renders the English text, not the key. |
| 18-06 | Users index, create and edit pages and the appearance settings show no hardcoded strings. |
| 18-07 | Validation messages and toasts on the users pages follow the active locale. |

## Constraints & Assumptions

- All strings of a page ship with every request (shared prop). Acceptable at current size; if the bag grows past ~30 KB, move to per-page namespaces via Inertia `once`/optional props.
- Octane: locale is set per request by middleware; no static state.
- Dates and numbers: formatting by locale is out of scope until a page needs it (tracked in the plan).
